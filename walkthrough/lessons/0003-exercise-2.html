2. מה נשמר לכל BBL?

struct BblData {
    ADDRINT address;
    UINT64 execCount;
    bool hasCondTail;
    UINT64 takenCount, fallthruCount;
    bool hasIndirectTail;
    unordered_map<ADDRINT, UINT64> indirectTargets;
};

המפתח ב־bblMap הוא כתובת תחילת ה־BBL. ה־record משלב שני סוגי מידע:

  • Node heat: כמה פעמים ה־BBL כולו התבצע.
  • Edge heat: לאיזה successor יצא הביצוע וכמה פעמים.
למה edge profile שימושי יותר? optimization משנה control flow. כדי להפוך target עקיף ל־direct, או להפוך branch כדי שהנתיב החם יהיה fall-through, צריך לדעת את התפלגות הקשתות — לא רק את מספר הכניסות ל־function.

3. Trace — לב הכלי

Find/create BBL recordכתובת ה־BBL מחברת אותו ל־BblData.
Count executionsBumpExec נשתלת פעם אחת ל־BBL.
Classify tailbranch תנאי או indirect control flow.
Track routine stateinstruction count ו־register writes בתוך ה־routine.

Conditional branch

if (INS_IsBranch(tail) && INS_HasFallThrough(tail)) {
    INS_InsertCall(tail, IPOINT_BEFORE, CondBranchCb,
                   IARG_PTR, bd,
                   IARG_BRANCH_TAKEN,
                   IARG_END);
}

IARG_BRANCH_TAKEN הוא boolean runtime. callback אחד מגדיל takenCount או fallthruCount.

Indirect branch

INS_InsertCall(tail, IPOINT_BEFORE, IndirectBranchCb,
               IARG_PTR, bd,
               IARG_BRANCH_TARGET_ADDR,
               IARG_BRANCH_TAKEN,
               IARG_END);

ה־target אינו מקודד ב־instruction; הוא מחושב מ־register או memory בזמן ריצה. Pin מעביר את הכתובת האמיתית, והמפה מגדילה count מלא לפי הכתובת המלאה.

זהו הזרע של de-virtualization: אם site הגיע 98% מהפעמים לאותה כתובת, TC2 יכול לבדוק את הכתובת ולנתב את המקרה החם ב־direct branch, עם fallback עקיף לשאר המקרים.

בתרגיל 1 היה מערך regSamples גלובלי. כאן כל RoutineData מחזיק שישה רצפים משלו. כאשר Trace מזהה את ה־routine, הוא מעביר pointer ל־rtnData->regs[i].

5. כתיבת הפלט

WriteEdgeProfile

  1. אוספת רק BBLs עם execCount > 0.
  2. ממיינת descending לפי heat.
  3. כותבת address ו־count.
  4. מוסיפה taken/fall-through כשקיים conditional tail.
  5. ממיינת target pairs ומגבילה לעשרה.

WriteRtnOutput

  1. ממיינת routines לפי dynamic instruction count.
  2. מדלגת על routines שלא בוצעו.
  3. כותבת metadata ומונים.
  4. כותבת samples ומחשבת average absolute delta.

Fini מפעילה את שתיהן אחרי סיום התוכנית.

7. הנחות ומגבלות

  • המפרט מניח application יחיד־thread; אין locks סביב המפות והמונים.
  • unordered_map בתוך analysis callback של indirect branch עלול להיות יקר.
  • ה־register samples הם 20 writes ראשונים לכל register/routine, לא מדגם סטטיסטי לאורך כל הריצה.
  • ה־BBL identity הוא address. אם Pin יוצר חלוקות דינמיות שונות באותה כתובת, צריך להבין כיצד ה־API מאחד או מפריד אותן.
  • direct unconditional target ידוע סטטית ולכן הפורמט אינו מדפיס רשימת targets עבורו; ה־BBL count כבר נותן את חום הקשת.

8. התרומה לפרויקט הסופי

BBL heat

קובע אילו sites שווים את מחיר האופטימיזציה.

Edge bias

מאפשר code reordering והיפוך Jcc כאשר taken חם מ־fall-through.

Target frequency

מאפשר לבחור target חם ל־de-virtualization.

אבל: הפרויקט לא יכול פשוט להעתיק את unordered_map של תרגיל 2 לתוך stub של קוד מכונה. הוא צריך מנגנון מדידה זול ומדויק בתוך TC — האתגר של תרגיל 4 ושל הרחבת ה־top-k בפרויקט.

בדיקת הבנה

אם BBL בוצע 1,000 פעמים, taken=900 ו־fall-through=100, מה ניתן לעשות בפרויקט?

אם ה־layout המקורי שם את taken כ־branch ואת fall-through כרצף, אפשר לשקול להפוך את התנאי ולהחליף יעדים כך שהקשת החמה תהפוך ל־fall-through. צריך לשמור semantics ולתקן targets.

למה indirect target חייב להיאסף בזמן ריצה?

כי הכתובת נקבעת מ־register/memory ולא מופיעה כ־immediate קבוע בתוך instruction. static decoder לבדו אינו יודע מה יהיה ה־target.

מה נותן לנו מיון hottest → coldest?

הוא מציב מיד בראש הפלט את הקוד שבו שינוי קטן יכול להשפיע על רוב זמן הריצה, וגם עוזר לבחור threshold לפרויקט.

אם execCount=500 ו־fallthruCount=120 ב־BBL שמסתיים ב־Jcc, מהו takenCount?

380. כל execution בוחר בדיוק אחת משתי הקשתות, ולכן taken = exec - fall-through.

Site עקיף הגיע ליעד A 9,700 פעמים וליעד B 300 פעמים. מה profile מוכיח ומה הוא לא מוכיח?

הוא מוכיח שבחלון שנמדד A קיבל 97% מן ההגעות. הוא אינו מוכיח ש־A יהיה היעד בכל input או phase עתידי, ולכן עדיין נדרש fallback ל־B וליעדים חדשים.

למה מפת targets מדויקת ב־callback עלולה לפגוע בביצועי profiler?

כל indirect execution עלול לבצע hash, חיפוש ולעיתים allocation. זו מדידה מדויקת אך יקרה; בפרויקט מחפשים מבנה bounded ופשוט יותר שנשאר מדויק ל־targets הנשמרים.

למה שני profilers תקינים יכולים לדווח מספר שונה של BBLs?

JIT ותרגום סטטי יכולים לחלק instructions לגבולות BBL שונים ולכסות images שונים. משווים counts רק לאחר שמוודאים שהכתובות והגבולות מייצגים אותו block.
