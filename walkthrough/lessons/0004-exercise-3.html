פרק 03 • Probe-mode Translation

תרגיל 3 — עכשיו אנחנו המתרגם

מתקנים Pintool שמפענח routines, מקודד אותן מחדש לתוך Translation Cache ומחליף את הכניסה המקורית. זהו המעבר מפרופיילר למערכת binary translation אמיתית.

חזרה למסלולהבא: תרגיל 4

1. הבעיה הרשמית

ה־Pintool שסופק, btranslate.cpp, קורס ב־Segmentation Fault בעת תרגום cpugcc_r_base.Oz-m64 ואינו מייצר 200.s. צריך לאתר את התקלה, לתקן, ולהוכיח שהפלט נכון.

<PIN_ROOT>/pin -t obj-intel64/btranslate.so -- \
  ./cpugcc_r_base.Oz-m64 200.i -o 200.s
השינוי העקרוני: בתרגילים 1–2 Pin יצר את הקוד ב־JIT. כאן הקוד שלנו מנהל decode → map → encode → relocation → copy → commit.

2. צינור התרגום המלא

1. Allocateממפים TC קרוב מספיק לקוד המקורי.
2. Decode to IRכל instruction הופכת ל־instr_map_t.
3. Relocateמקשרים targets ומתקנים branch/RIP displacements.
4. Commitכותבים ל־TC ומחליפים routine heads ב־probes.

שלב 1 — allocate_and_init_memory

הפונקציה סורקת executable sections, מעריכה מספר instructions וגודל code, ואז עושה mmap לאזור RWX. הקרבה לקוד המקורי חשובה משום ש־x86-64 branches ו־RIP-relative operands משתמשים לרוב ב־signed 32-bit displacement, כלומר בערך ±2GB.

שלב 2 — find_candidate_rtns_for_tc

לכל section executable ולכל routine בטוחה:

  1. RTN_Open.
  2. מעבר על instructions.
  3. xed_decode מהבתים המקוריים.
  4. add_new_instr_entry שומר address מקורי, target, RIP target, bytes מקודדים וסוג instruction.
  5. RTN_Close.

שלב 3 — Chaining

entry_map ממפה כתובת instruction מקורית ל־index ב־instr_map. direct branch ש־target שלו תורגם מקבל targ_map_entry אל העותק החדש. כך branch בתוך TC יכול להגיע ל־TC ולא לקוד המקורי.

שלבים 4–5 — כתובות ו־fixups

תחילה מחשבים כתובת TC משוערת לכל entry. אחר כך מקודדים מחדש:

  • RIP-relative memory operand לכיוון data המקורי.
  • direct branch/call לכיוון target המתורגם.
  • branch/call ל־target שלא תורגם — חזרה לקוד המקורי.

מכיוון שקידוד חדש יכול לשנות instruction size, ה־fixup pass חוזר עד שהגדלים והכתובות מתייצבים.

שלבים 6–7 — Copy ו־Commit

copy_instrs_to_tc מעתיק את encoded_ins לכתובות המחושבות. לאחר מכן commit_translated_rtns_to_tc קורא ל־RTN_ReplaceProbed בכל RtnHeadIns, ולכן כניסה ל־routine המקורית קופצת לעותק ב־TC.

3. ה־IR הפשוט: instr_map_t

typedef struct {
    ADDRINT orig_ins_addr;   // מיקום מקורי
    ADDRINT new_ins_addr;    // מיקום ב-TC
    ADDRINT orig_targ_addr;  // branch/call target
    ADDRINT orig_rip_addr;   // RIP-relative data target
    ins_enum_t ins_type;     // Regular / routine head
    char encoded_ins[15];    // bytes לקידוד החדש
    unsigned size;
    int targ_map_entry;      // target בתוך ה-IR
} instr_map_t;

זו אינה compiler IR עשירה כמו LLVM. היא “machine-level IR”: עדיין instruction x86, אבל עם metadata שמאפשר להזיז אותה בבטחה.

4. התקלה שאותרה — תרגום .plt

הצוות הוסיף knob בשם -max_rtns N והפעיל binary search: אם תרגום N routines עובד ו־N+1 קורס, routine מספר N+1 חשודה. התקלה הצטמצמה ל־routine השנייה ש־Pin דיווח עליה: .plt.

Call לסמל חיצונימגיע ל־PLT stub.
First callה־stub מכין מידע ל־dynamic linker.
Probe על PLT0דורס את ההתחלה ומעביר את handshake לעותק לא מתאים.
ld.so מקבל state שגויlazy binding נשבר ונוצר SIGSEGV.

.plt אינו function רגיל, אף ש־Pin עלול להציג אותו כ־RTN. הוא רצף stubs של lazy binding שמסתמך על layout ו־GOT מדויקים.

התיקון: לדלג על sections ממשפחת .plt ולא לבצע להן probe replacement. direct calls מן TC אל PLT חוזרים אל הכתובת המקורית דרך jump_to_orig_addr_map.

5. תיקוני robustness נוספים בהגשה

בעיהלמה היא מסוכנתתיקון
Off-by-one ב־jump_to_orig_addr_mapslot 0 מתבזבז ו־dedup מפספס את ה־entry האחרון.בדיקת bounds, שימוש ב־index הנוכחי ורק אז increment.
1-byte displacementLOOP/JRCXZ מסוגלות רק ±128; truncation קופץ לזבל.לזהות overflow ולבטל תרגום בצורה נקייה.
Routine לא בטוחה ל־probeהחלפה עלולה להיכשל או להשחית code.סינון עם RTN_IsSafeForProbedReplacement.
Routine קטנה מ־5 bytesאין מקום ל־probe jump.להשאיר אותה בקוד המקורי.
Jcc ליעד שלא תורגםאין ל־Jcc צורת memory-indirect כמו JMP/CALL.לקודד rel32 ישירות חזרה ל־target המקורי.

6. src_fixed — הרחבה ניסויית, לא ההגשה

לאחר ההגשה נבנה variant נפרד שמטפל טוב יותר ב־binaries סטטיים גדולים כגון sgcc_base/sgcc_peak.

  • העברת instr_map אל heap: היא bookkeeping בלבד ואינה צריכה לשבת בתוך mmap executable. כך jump_to_orig_addr_map נשאר קרוב ל־TC ולא נדחף מעבר ל־2GB.
  • דילוג על .init/.fini: אלה startup/teardown stubs, לא functions רגילות.

ה־README של ההגשה מתאר גם התאמות נוספות שנבדקו לאורך הדרך: הצבת TC הרחק מ־brk של binary סטטי, דילוג על routines מוקדמות של TLS/brk, וצמצום sizing מופרז.

בהגנה יש לדייק: אל תייחסו אוטומטית כל שינוי ב־src_fixed להגשה המקורית. אמרו מה היה תיקון המטלה ומה נוסף מאוחר יותר לצורך הבינארים של תרגיל 4.

7. התרומה לפרויקט הסופי

Translation pipeline

TC2 משתמש שוב באותם שלבי chain → address → fix → copy.

Correct fallback

de-virtualization חייבת להשאיר indirect path ל־target שלא התמחה.

Probe discipline

routine heads, patch width ו־bootstrap sections נשארים load-bearing.

בלי תרגיל 3 אפשר לדעת מה חם, אבל אי אפשר לייצר גרסה חדשה. הפרויקט מחבר את ה־profile של תרגיל 2 אל יכולת ה־code generation של תרגיל 3.

בדיקת הבנה

למה צריך לחשב new_disp אחרי שיודעים את new_ins_addr?

כי displacement יחסי תלוי גם במיקום instruction החדשה וגם באורכה. לפני שקובעים layout וקידוד, המרחק החדש אינו ידוע.

למה דילוג על .plt אינו “ויתור על תרגום כל התוכנית”?

זהו fallback מכוון: routines רגילות רצות ב־TC, אך stubs רגישים נשארים מקוריים. branches מה־TC יכולים לחזור אליהם ולשמור על lazy binding תקין.

מה מלמדת שיטת -max_rtns?

מינימיזציה לפני תיקון: מצמצמים את קבוצת routines עד שמבודדים את הראשונה שהוספתה הופכת run תקין לקריסה.

למה decode והעתקה byte-for-byte אינם מספיקים לבניית TC?

כי branches ו־RIP-relative operands מקודדים מרחק מן המיקום הישן. לאחר relocation אותם bytes מצביעים לכתובת אחרת, ולכן צריך encode מחדש ו־fixups.

מה ההבדל בין chaining לבין commit?

Chaining מחבר branches בתוך הקוד המתורגם ל־targets מתורגמים. Commit משנה את כניסת ה־routine המקורית בעזרת Pin כך שהביצוע יתחיל בעותק שב־TC.

Branch קצר דורש מרחק בטווח -128..127, אך לאחר הוספת קוד המרחק הוא 240. מה אסור לעשות?

אסור לחתוך את 240 ל־byte; הוא יעטוף וינחת במקום שגוי. צריך להרחיב ל־encoding מתאים אם אפשר, או להשאיר את ה־routine לא מתורגמת.

למה verifier של targets חשוב גם כשהתוכנית מסיימת עם exit code 0?

נתיב פגום יכול להיות קר ולא להתבצע ב־input הנוכחי. verifier סטטי של ה־TC מגלה branch שנוחת באמצע instruction עוד לפני שהנתיב נלקח.
