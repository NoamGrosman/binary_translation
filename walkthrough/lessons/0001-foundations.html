מה בכלל קורה כאן?

לפני שנכנסים לקוד: מהו Pintool, מה ההבדל בין JIT ל־Probe, מהו Translation Cache, ואיך instruction הופכת לנתון שאפשר להזיז, למדוד ולשנות.

חזרה למסלולהבא: תרגיל 1

1. המודל המנטלי

התוכנית המקורית היא אוסף בתים של מכונת x86-64. Pin יושב בין קובץ ההרצה לבין המעבד ונותן לנו לצפות בקוד, להוסיף לו פעולות, או להפנות את הביצוע לעותק חדש.

Original binaryבתים וקוד מכונה כפי שקימפל ה־compiler.
Decodeפענוח הבתים ל־instructions, operands, targets וקטגוריות.
Transformהוספת counters, שינוי branch או סידור מחדש.
Translation Cacheאזור זיכרון executable שבו נשמר ומבוצע הקוד החדש.
העיקרון המאחד: “translate once, execute many”. עלות הבנייה משתלמת רק אם הקוד המתורגם ירוץ שוב ושוב.

2. Pin בשתי צורות עבודה

JIT mode

Pin מגלה code בזמן ריצה, בונה traces ו־BBLs בקוד cache פנימי, ומכניס calls לפונקציות analysis שב־Pintool.

  • כיסוי דינמי רחב, כולל shared libraries.
  • Pin מטפל בשמירת state סביב analysis calls.
  • מתאים במיוחד ל־profiling — תרגילים 1–2.
TRACE_AddInstrumentFunction(Trace, 0);
PIN_StartProgram();

Probe mode

התוכנית רצה כמעט native. Pin מחליף תחילת routine ב־jump קצר לכתובת חלופית; האחריות על תקינות הקוד החדש עוברת אלינו.

  • פחות overhead.
  • Static discovery עלול לפספס גבולות.
  • relocations, flags ו־registers הם באחריות המתרגם — תרגילים 3–4 והפרויקט.
RTN_ReplaceProbed(rtn, translated_addr);
PIN_StartProgramProbed();

4. Instrumentation מול Analysis

זו הבחנה שחוזרת כמעט בכל שורת Pin:

Instrumentation time

ה־Pintool מסתכל על מבנה הקוד ומחליט איפה לשתול עבודה. לדוגמה, BBL_InsertCall מוסיף callback לכל BBL.

Analysis time

הקוד שנשתל רץ בכל פעם שהיישום מגיע לנקודה. לדוגמה, BumpExec מגדיל counter בזמן ריצה.

// instrumentation: runs when Pin builds a trace
BBL_InsertCall(bbl, IPOINT_ANYWHERE, AFUNPTR(BumpExec),
               IARG_PTR, &data.execCount, IARG_END);

// analysis: runs whenever that BBL executes
VOID BumpExec(UINT64* p) { (*p)++; }
למה זה חשוב לביצועים? instrumentation רצה מעט פעמים; analysis עלולה לרוץ מיליוני פעמים. לכן גם instruction אחת מיותרת בתוך stub חם יכולה להיות יקרה.

5. למה אי אפשר פשוט לעשות memcpy לקוד?

כתובות יחסיות תלויות במקום שבו instruction נמצאת. אם מעבירים אותה מכתובת מקורית אל TC, אותו displacement עלול להצביע ליעד אחר.

Direct branch

Jcc/JMP/CALL rel32 שומר מרחק יחסי אל target. צריך לחשב מרחק חדש.

RIP-relative data

MOV rax,[rip+disp] מצביע לנתון לפי RIP החדש. צריך לקודד displacement חדש.

Target שלא תורגם

אם היעד נשאר בקוד המקורי, צריך branch חזרה למקור — לעיתים דרך טבלת כתובות.

new_disp = target_address - new_instruction_address - new_instruction_size

זו הסיבה שתרגיל 3 בונה instr_map, מבצע chaining, מעריך כתובות, מתקן displacements בכמה איטרציות ורק אז כותב את הבתים ל־TC.

6. חוזה הנכונות

מתרגם נחשב נכון רק אם התוכנית אינה יכולה להבחין שהקוד הועבר או שונה.

  • אותם values ב־registers החיים.
  • אותם status flags כשקוד המשך משתמש בהם.
  • אותו control flow, גם ל־target נדיר שלא הופיע בפרופיל.
  • אותו stack ו־return address, במיוחד סביב CALL/RET.
  • אותו פלט byte-for-byte ו־exit code תקין.
“התוכנית לא קרסה” אינו מבחן מספיק. תרגיל 4 תיעד מקרה שבו clobber של RFLAGS יצר פלט שגוי למרות שהריצה הסתיימה. ההשוואה ל־native golden היא מקור האמת.

בדיקת הבנה

למה תרגילים 1–2 יכולים להסתפק ב־callbacks ואילו תרגיל 3 צריך XED?

ב־JIT mode, Pin בונה וממקם את הקוד ומאפשר להכניס analysis calls. בתרגיל 3 אנחנו עצמנו מעתיקים instructions לכתובות חדשות; לכן חייבים לפענח, לקודד מחדש ולתקן address-dependent fields.

מה ההבדל בין BBL ל־routine?

routine היא פונקציה שלמה כפי שזוהתה בסמלים/ב־static discovery. BBL הוא רצף קטן עם כניסה אחת ויציאה אחת. routine כוללת בדרך כלל BBLs רבים.

מהו מבחן הנכונות החשוב ביותר בפרויקט?

exit code אפס ופלט תוכנית byte-identical ל־native golden בכל ריצה נמדדת. dumps ו־verifiers מסבירים את התקינות, אך אינם מחליפים את התוצאה החיצונית.
