2. הבעיה שהפרויקט פותר

תרגילים 1–4 יודעים למדוד קוד ולתרגם אותו, אבל עדיין אינם משתמשים ב־profile כדי לייצר גרסה חדשה שמותאמת להתנהגות runtime. הפרויקט סוגר את הלולאה:

Translateהמרת routines מן ה־binary אל TC1.
Observeספירת BBLs ויעדים של indirect JMP/CALL.
Decideבחירת sites ו־layout לפי profile.
Generateיצירת TC2 נקי ומותאם.
Switchהפניית routine heads מ־TC1 אל TC2.

המדד Translated code run took מתחיל לאחר בניית TC1 ומסתיים ב־exit, ולכן הוא כולל את כל המחיר האמיתי:

Thread פנימי ממתין N שניות, מפסיק את איסוף ה־profile, בונה את TC2 באזור נפרד, מבצע fixups ו־verification, ואז commit_translated_rtns_to_tc2 משנה את הכניסות השמורות ב־TC1 ל־jumps אל TC2.

למה לא patch בתוך TC1? Guard ו־layout חדש משנים את אורכי ה־instructions ואת המרחקים בין targets. Cache נפרד מאפשר לבנות, לקודד ולבדוק הכול לפני שמפנים אליו execution.

4. מה TC1 מודד — ומה שופר לעומת תרגיל 4?

BBL profile

מונה executions ו־fall-through לכל block. מכאן נגזרים heat ו־edge bias עבור reordering.

Indirect targets

גם indirect JMP וגם indirect CALL מסיימים BBL ומקבלים target profile; תרגיל 4 התמקד בקפיצות.

Exact top-4 במקום hash מאבד

בשלד, target & 3 בוחר אחד מארבעה buckets. כתובות שונות מתנגשות, ולכן address ו־count עלולים לייצג דברים שונים. בפרויקט כל site מחזיק עד ארבעה pairs מדויקים של כתובת מלאה ומונה.

  • אם ה־target כבר נמצא — מגדילים את המונה שלו.
  • אם יש slot פנוי — מכניסים address חדש עם count התחלתי.
  • אם ארבעת ה־slots מלאים — target נוסף נזרק. זו הטיה שמרנית: site עשוי לא לעבור threshold, אך לא ייבנה guard על כתובת שהתנגשה.
  • עדכון הטבלה שומר RFLAGS, משום שתוכנית אמיתית יכולה לשאת תוצאת compare דרך indirect jump.

5. שלושת ה־passes המרכזיים בבניית TC2

  1. Profiling-stub stripping: entries שמסומנים כ־profiling וגם NOPs מוסרים מן ה־TC2. בניגוד לשלד המקורי, לא נשאר body מושבת שממשיך לתפוס I-cache ולבצע jumps.
  2. De-virtualization: sites חמים ודומיננטיים מקבלים guard, direct fast path ו־fallback עקיף.
  3. Code reordering: BBLs בכל routine חמה מסודרים בשרשראות לפי successor חם; תנאי מתהפך כשצריך כדי להפוך את הקשת החמה ל־fall-through.

לאחר יצירת ה־IR החדש, אותו מנגנון מתרגיל 3 מחשב addresses, מקודד מחדש branches ו־RIP-relative operands, כותב bytes ל־TC2 ומבצע commit.

6. De-virtualization — ה־optimization החובה

הרעיון הסמנטי

computed = evaluate the original indirect operand
if (computed == hottest_profiled_target)
    direct jump/call to that target's TC2 translation
else
    execute the original indirect jump/call using computed

ה־guard שומר את ה־state הדרוש, מחשב פעם אחת את ה־target המקורי, משווה אותו ל־target החם ומשחזר registers ו־flags בשני הנתיבים. ה־fast path נשאר בתוך TC2; ה־fallback שומר correctness גם אם ה־profile לא חזה את ה־target הנוכחי.

תנאי ההפעלה בפועל

recorded_hits >= 1000        (-devirt_min, default 1000)
top_target_share >= 70%     (-devirt_pct, default 70)
target has a TC2 translation and can be encoded safely

ב־profile המתועד של cc1, 212 מתוך 371 sites בעלי target data עברו את סף ה־hits, 111 מהם עברו גם 70% dominance, ובזמן בניית TC2 בוצעה de-virtualization ל־103 מתוך 385 candidates שנראו.

CALL לעומת JMP: direct CALL חייב לחזור ל־continuation הנכון ולדלג מעל fallback לאחר החזרה. JMP אינו חוזר. זו הסיבה שה־emitter מטפל בשני הסוגים בנפרד אף שה־guard דומה.

7. האופטימיזציה השנייה — Profile-guided Code Reordering

לכל routine שקיבלה heat, הבונה מתחיל ב־BBL שלא שובץ, ממשיך שוב ושוב אל ה־successor החם ביותר שעדיין פנוי, וכך יוצר hot traces רציפים בזיכרון.

מה קורה ל־conditional branch?

  • אם ה־fall-through המקורי הוא ה־successor החם והוא ממוקם מיד אחריו — אין צורך לשנות דבר.
  • אם ה־taken successor חם יותר — הופכים את condition של ה־Jcc ומחליפים בין שני ה־successors, כך שהנתיב החם נהיה fall-through.
  • אם ה־fall-through הלוגי אינו סמוך פיזית לאחר reorder — מוסיפים JMP מפורש כדי לשמור semantics.

המטרה כפולה: פחות branches taken במסלול החם ו־locality טובה יותר ב־I-cache. ההיפוך אינו “משנה החלטה”; הוא משנה encoding ו־layout יחד כך שאותם שני נתיבים נשמרים.

10. איך ה־scripts מוכיחים נכונות ומדידה הוגנת?

Correctness gate

  • exit code חייב להיות 0.
  • הפלט מושווה ל־golden בעזרת cmp/hash.
  • נדרש TC2 commit חיובי; run שנפל בחזרה ל־native אינו datapoint.
  • -verify_tc בודק branch ו־RIP-relative targets.

Measurement gate

  • warm-up נזרק.
  • סדר הזוגות מתחלף baseline/opt ואז opt/baseline.
  • אותו input ואותו prof_time.
  • median מחושב רק אם כל run עבר correctness.
improvement = 100 * (baseline_median - project_median)
                    / baseline_median

11. Invariants שאסור לשבור

  • כל direct target ב־TC2 נוחת בתחילת instruction מוכרת.
  • ה־fallback מחשב ומשתמש בדיוק ב־target של ה־instruction המקורית.
  • RAX, RBX ו־RFLAGS מוחזרים לערך הנכון בשני נתיבי ה־guard.
  • Direct CALL וה־fallback חוזרים לאותו continuation.
  • Jcc inversion מחליף גם condition וגם successors; observable control flow נשאר זהה.
  • כל fall-through שכבר אינו adjacent מקבל jump מפורש.
  • TC2, maps ו־spill slots אינם חופפים ואינם חורגים מן האזור שהוקצה.
  • מהירות אינה evidence אם הפלט אינו זהה או אם אף routine לא הועברה ל־TC2.

בדיקת הבנה וחזרה להגנה

למה stripping של profiling stubs נחשב שיפור בפני עצמו?

לאחר חלון ה־profile אין צורך להמשיך לשלם instructions, branches ו־I-cache footprint של גוף ה־stub. TC2 משאיר רק את קוד התוכנית ואת transformations החדשות.

למה direct fast path לבדו אינו de-virtualization נכונה?

Profile הוא observation ולא הבטחה. target נדיר או חדש עדיין אפשרי; ללא fallback התוכנית תבצע control flow שגוי.

Site קיבל 900 hits ו־99% dominance. האם ברירת המחדל תבצע de-virtualization?

לא. הוא נכשל בסף המינימלי של 1,000 hits, גם אם ההתפלגות מונומורפית מאוד. המטרה היא לא לשלם guard ו־code bloat על site קר.

Site קיבל 100,000 hits אך target העליון מחזיק 45%. למה הוא נדחה?

ה־guard ייכשל ברוב ההגעות ויוסיף עבודה לפני ה־indirect branch המקורי. זה site חם אבל polymorphic, ולכן de-virtualization ליעד יחיד אינה משתלמת.

למה exact top-4 עם overflow drop בטוח יותר מ־target & 3?

כל count שנשמר שייך לכתובת המלאה המתאימה. זריקת target עשויה למנוע optimization, אך collision אינו יכול לגרום לבחירת כתובת שגויה.

אם הופכים JNZ ל־JZ בלי לשנות layout או targets, האם זו reordering נכונה?

לא. רק condition התהפך ולכן משמעות התוכנית השתנתה. צריך להחליף בין taken/fall-through successors ולהוסיף jump אם successor לוגי אינו adjacent.

למה baseline צריך לכלול את תיקוני הנכונות של הפרויקט?

כדי שהפרש הזמן ימדוד את האופטימיזציות בלבד. Baseline שקורס, נופל ל־native או משחית output אינו נקודת השוואה הוגנת.

איך עונים אם שואלים האם ה־audit הושלם?

אומרים במדויק: build, goldens ושחזורי bzip2/cc1 עברו; ledger האדברסרי עדיין מחזיק leads פתוחים. מבדילים בין evidence מאומת לבין עבודה שטרם קיבלה verdict.
