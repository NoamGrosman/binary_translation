2. ההסבר של דקה אחת

נוסח לתרגול:
“הפרויקט שלנו הוא optimizer בינארי דו־שלבי. תחילה אנחנו מתרגמים routines אל TC1 ומוסיפים counters לכל basic block וליעדים של indirect jumps ו־calls. אחרי חלון profiling, thread בונה TC2 ומסיר ממנו את קוד המדידה. ב־TC2 אנחנו מתמחים sites חמים: אם target runtime שווה ל־target המדויק והדומיננטי מן ה־profile, עוברים ב־direct branch; אחרת נשאר fallback עקיף. בנוסף אנחנו מסדרים basic blocks לפי hot paths והופכים branch condition כשהדבר הופך את הקשת החמה ל־fall-through. לבסוף אנחנו מפנים את ה־routines ל־TC2 ומשווים elapsed time מול baseline בעל אותם תיקוני נכונות, כאשר כל timed run חייב להפיק פלט byte-identical ל־native ולהראות commit אמיתי ל־TC2.”

3. שאלות קשות שסביר שישאלו

למה לא להחליף תמיד indirect branch ב־direct branch ל־target החם?

כי profile הוא observation מוגבל. input או phase אחר יכולים להביא target אחר. ה־guard וה־fallback שומרים semantics לכל target.

איך אתם יודעים שה־target החם מדויק?

לא משתמשים ב־target & 3 lossy buckets. שומרים exact address/count pairs, מציגים dump וסכומי counts, ומפעילים transformation רק כאשר count ו־dominance עוברים threshold מתועד.

מה ההבדל בין de-virtualization של CALL ושל JMP?

CALL יוצרת return address וצריכה לחזור ל־continuation זהה בשני הנתיבים. בנוסף ABI ו־live state סביב call שונים. JMP אינו חוזר לנקודת ה־site.

מה קורה אם ה־guard משנה flags?

אם flags חיים, זו פגיעה ב־semantics. צריך analysis שמוכיח שהם מתים, רצף flag-transparent, או save/restore מדויק. הלקח הזה נבדק כבר בתרגיל 4.

למה צריך TC2? אי אפשר patch ישירות את TC1?

TC2 מאפשר לבנות layout חדש ו־instruction sequences באורך שונה הרחק מן הקוד שרץ, לבצע chaining/fixups ואימות, ואז לעבור אליו. patching in place מורכב ומסוכן יותר.

מה נכלל במספר elapsed time?

מהסיום של בניית TC1 ועד exit: חלון profiling, זמן בניית TC2 והריצה ב־TC2. לכן מדד השיפור אינו מסתיר את עלות האופטימיזציה.

איך baseline נשאר הוגן?

אותו codebase, אותם תיקוני נכונות, אותה תשתית gearing ואותו prof_time; רק transformations האופטימיזציה כבויות. אחרת משווים apples to oranges.

למה median וריצות interleaved?

זמן מערכת מושפע מרעש. alternating order מפחית bias של חימום או load משתנה; median עמיד יותר ל־outliers.

למה profile counts של gcc עשויים להשתנות?

ASLR, pointer-keyed structures והתנהגות runtime יכולים להזיז counts גם בין שתי ריצות של אותו tool. נכונות נמדדת בפלט התוכנית; optimization decision צריכה להיות robust לרעש.

מהו הכשל הכי מסוכן שלא נראה כקריסה?

clobber של live register או flags שמייצר פלט שגוי אך exit 0. לכן משווים bytes מול native בכל timed run.

למה ספי ברירת המחדל הם 1,000 hits ו־70% dominance?

ה־guard מוסיף בערך עשר instructions לכל execution. מתחת ל־1,000 hits החיסכון קטן ביחס ל־overhead ול־code bloat; מתחת ל־70% רוב גדול מדי מן ההגעות משלם guard ואז fallback. ב־cc1 המדוד הספים יושבים קרוב להפרדה הטבעית בין sites דומיננטיים ל־polymorphic.

מה בדיוק עושה code reordering במימוש?

הוא מסדר BBLs של routine לפי שרשרת successors חמה. אם taken edge של Jcc היא החמה, הופכים את ה־condition כך שהיא תהפוך ל־fall-through; אם successor לוגי אינו adjacent לאחר הסידור, מוסיפים jump מפורש.

האם ה־audit האדברסרי הסתיים?

לא. Clean build, כל native goldens ושחזורי bzip2/cc1 עברו, אך ledger עדיין מחזיק leads פתוחים לגבי גבולות TC/TC2, dump profile והדפסת debug. מציגים זאת בגלוי ולא מערבבים בין evidence שעבר לבין verdict שטרם ניתן.

4. Checklist לפני ההגנה

Code evidence

  • line map לפונקציות המרכזיות.
  • dump של TC1 ו־TC2.
  • site אחד מוסבר instruction-by-instruction.
  • invariant list.
  • fallback מוכח.

Measurement evidence

  • native golden hashes.
  • לפחות 5 alternating pairs.
  • raw rows זמינות.
  • median וחישוב אחוז.
  • גרף עם labels ויחידות.
להציג את שכבות ה־evidence בנפרד. מספרי README הם מדידות ההגשה; שחזור audit חדש נתן 19.07% ב־bzip2 ו־46.75% ב־cc1. אין להציג smoke run יחיד כאילו היה benchmark רב־ריצות, ואין לומר שה־audit סגור כל עוד קיימים leads פתוחים.

5. כרטיסיות בזק

TC

אזור executable שמכיל code מתורגם.

BBL heat

מספר executions של basic block.

Edge bias

התפלגות execution בין successors.

Chaining

חיבור branch ל־target המתורגם במקום למקור.

Liveness

האם value ישן ייקרא לפני overwrite.

Gearing

מעבר בין TC1 שמודד ל־TC2 שמותאם.

De-virtualization

guard + direct hot path + indirect fallback.

Relocation

תיקון address-dependent encoding לאחר הזזה.

Correctness

אותו observable behavior, לא רק “לא קרס”.

6. מה להכין פיזית לפני ההגנה?

  • פתיחה מהירה של src/project.cpp באזור ה־knobs, ה־guard ובניית TC2.
  • דוגמת indirect site אחת: target counts, החלטת threshold ו־disassembly של fast path/fallback.
  • דוגמת routine אחת לפני ואחרי reordering, עם taken/fall-through counts.
  • טבלת README לצד שחזור audit, בלי לערבב בין סדרות המדידה.
  • שורת פקודה אחת שמריצה -verify_tc ומשווה output ל־golden.
  • תשובה שקופה למצב ה־audit ולשלושת ה־leads הפתוחים.

החומר כבר קיים בתיקיית WSL; המטרה כעת היא לבחור evidence קטן וברור שאפשר להסביר בלי לחפש בזמן אמת בין לוגים גדולים.
