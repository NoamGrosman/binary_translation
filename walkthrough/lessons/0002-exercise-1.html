תרגיל 1 — מי עובד וכמה?

Profiler ב־JIT mode שממפה routines, סופר כמה instructions בוצעו וכמה פעמים routine נקראה, ובנוסף דוגם values שנכתבו לשישה registers.

חזרה למסלולהבא: תרגיל 2

1. מה מטרת התרגיל?

הערת מקור: אין בתיקייה PDF של תרגיל 1. ההסבר כאן נגזר מן הקוד ex1/ex1.cpp, מה־CSV שנשמרו, ומהאופן שבו תרגיל 2 מרחיב את אותו קוד.

התרגיל מלמד את “השלום עולם” של dynamic instrumentation: לא משנים את binary המקורי, אלא מבקשים מ־Pin להוסיף פעולות ספירה בזמן שהוא בונה את הקוד ב־JIT.

Routine identity

שם image, כתובת בסיס, שם routine וכתובת routine.

Dynamic heat

מספר instructions שבוצעו בתוך routine ומספר הכניסות אליה.

Register samples

עד 20 values ראשונים לאחר writes ל־RAX/RBX/RCX/RDX/RSI/RDI.

2. מבני הנתונים

struct RoutineData {
    string imageName;
    ADDRINT imageAddress;
    string routineName;
    ADDRINT routineAddress;
    UINT64 instructionCount;
    UINT64 callCount;
};

static RoutineData routinesArray[1000];
static map<ADDRINT, RoutineData*> rtnAddrToData;

לכל routine נשמר record קבוע. המפה מחברת כתובת routine אל record, כדי ש־callback של trace יוכל למצוא במהירות לאיזה מונה להוסיף.

המערכים הם static, ולכן C++ מאתחל את המונים וה־sample counts לאפס לפני main.

למה כתובת היא key? שמות routines אינם בהכרח ייחודיים בין libraries. כתובת runtime היא הזהות שנוחה ל־Pin בזמן הביצוע.

3. זרימת הביצוע

mainמאתחל symbols ואת Pin ורושם callbacks.
Routineנוצר record לכל RTN ונשתלת ספירת call בכניסה.
Traceעובר על BBLs ונשתלת ספירת instructions.
Analysis callbacksמגדילים מונים ודוגמים register values בזמן אמת.
FINIממיין וכותב rtn-output.csv.

Routine(RTN rtn) — בניית קטלוג routines

  1. קוראת את RTN_Address ונמנעת מכפילויות.
  2. שומרת שם וכתובת של ה־routine ושל ה־image שמכיל אותה.
  3. פותחת את ה־routine בעזרת RTN_Open.
  4. מכניסה CountRoutineCall ב־IPOINT_BEFORE.
  5. סוגרת עם RTN_Close.
RTN_InsertCall(rtn, IPOINT_BEFORE,
               (AFUNPTR)CountRoutineCall,
               IARG_PTR, &myData->callCount,
               IARG_END);

בכל כניסה ל־routine, פונקציית analysis מקבלת pointer ישיר למונה שלה ומבצעת ++.

Trace(TRACE trace) — ספירת עבודה

הקוד מזהה לאיזו routine שייך ה־trace. לכל BBL הוא שותל call שמוסיף BBL_NumIns(bbl) למונה. אם BBL בן 7 instructions רץ 100 פעמים — הוא תורם 700.

BBL_InsertCall(bbl, IPOINT_ANYWHERE,
               (AFUNPTR)CountBblInstructions,
               IARG_PTR, &data->instructionCount,
               IARG_UINT32, BBL_NumIns(bbl),
               IARG_END);

IPOINT_ANYWHERE נותן ל־Pin לבחור נקודה חוקית וזולה בתוך ה־BBL, כי מבחינת counter לא משנה באיזו instruction הוא גדל.

4. דגימת registers

עבור כל instruction שיש לה fall-through, הקוד בודק אם היא כותבת אחד מששת ה־registers. אם כן, הוא שותל callback אחרי ה־instruction ומעביר את value החדש:

if (INS_RegWContain(ins, TRACKED_REGS[i])) {
    INS_InsertCall(ins, IPOINT_AFTER, RecordRegValue,
                   IARG_UINT32, i,
                   IARG_REG_VALUE, TRACKED_REGS[i],
                   IARG_END);
}

הדגימה נעצרת לאחר 20 writes לכל register. בסיום מחושב:

average_delta = Σ |value[i] - value[i-1]| / (sample_count - 1)
משמעות, לא נבואה: average delta הוא תיאור גס של השינויים בדגימות הראשונות. הוא אינו אומר שה־register תמיד מתקדם בקצב הזה, ואינו מזהה stride של load/store באופן אמין.

5. הפלט

לפני הכתיבה, routines ממוינות לפי instructionCount מהחמה לקרה. שורת routine טיפוסית:

/path/to/tst, 0x400000, bar, 0x4004d2, 6000, 1000
שדהפירוש
/path/to/tstה־image שבו routine נמצאת.
0x400000כתובת הבסיס של ה־image.
barשם ה־routine.
0x4004d2כתובת הכניסה ל־routine.
6000מספר instructions דינמי, לא גודל סטטי.
1000מספר הפעמים שה־routine נקראה.

לאחר שורות ה־routines מתווספות שש שורות register samples גלובליות.

6. מה התרגיל עדיין לא פותר?

  • ה־register samples גלובליים לתוכנית, לא נשמרים לכל routine. תרגיל 2 מתקן זאת.
  • המגבלה היא 1,000 routines; מעבר לכך המידע נחתך בשקט.
  • אין synchronization. המימוש מניח בפועל שאין תחרות בין threads על המונים.
  • instructions בלי fall-through אינן נדגמות ב־IPOINT_AFTER, ולכן writes שמתרחשים ב־control-flow instructions עלולים לא להיכלל.
  • הכלי יודע “כמה חמה function”, אך לא איזה נתיב בתוכה חם.
וזו בדיוק הקפיצה לתרגיל 2: עוברים מרמת routine לגרף של basic blocks וקשתות, ושומרים register samples בתוך ה־routine שאליה הם שייכים.

7. התרומה לפרויקט הסופי

מכניקת Pin

רישום callbacks, העברת pointers כ־IARG ושימוש ב־runtime values הם הבסיס לכל איסוף profile.

רעיון ה־heat

מיון לפי עבודה דינמית מכניס את העיקרון שהאופטימיזציה צריכה להתמקד בקוד חם, לא בקוד גדול.

עם זאת, הפרויקט לא יכול לבחור de-virtualization על בסיס “routine חמה” בלבד. הוא צריך לדעת איזה indirect site חם ולאיזה target הוא מגיע — מידע שמתחיל בתרגיל 2.

בדיקת הבנה

למה מוסיפים BBL_NumIns בכל execution ולא פשוט סופרים את מספר ה־instructions ב־routine?

כי רוצים dynamic instruction count. BBL בתוך loop עשוי להתבצע מיליוני פעמים, בעוד BBL קר באותה routine מתבצע פעם אחת.

למה ה־register callback מוכנס אחרי instruction?

כדי לקבל את value שנכתב, לא את value שהיה לפני ה־write.

מהו החיסרון המרכזי של דגימות register בתרגיל 1?

הן גלובליות לתוכנית; אי אפשר לייחס רצף values ל־routine מסוימת. תרגיל 2 מעביר מערך samples לתוך RoutineData.

Routine מכילה 10 instructions ונקראה 100 פעמים. האם instructionCount חייב להיות 1,000?

לא. זה היה נכון רק אילו כל עשר ה־instructions בוצעו בכל קריאה. branches, early returns ו־loops גורמים ל־dynamic count להיות תלוי בנתיב בפועל.

למה מעבירים ל־callback מצביע ישיר אל המונה ולא את כתובת ה־routine?

כך analysis callback מבצע increment פשוט בלי לחפש שוב record במפה בכל execution. עבודת החיפוש נעשית בזמן instrumentation, וה־hot path נשאר קצר.

מה יקרה אם התוכנית מרובת־threads ושני threads יגדילו יחד את אותו מונה?

++ רגיל אינו atomic, ולכן updates עלולים ללכת לאיבוד. המימוש מתאים להנחת single-thread; לתוכנית מקבילית נדרשים counters לכל thread או synchronization.

איך היית מסביר במשפט אחד את ההבדל בין code size לבין dynamic instruction count?

Code size אומר כמה instructions קיימות סטטית; dynamic count אומר כמה instruction executions התרחשו בפועל, כולל חזרות של loops וקריאות חוזרות.
