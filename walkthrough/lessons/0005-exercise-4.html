פרק 04 • Probe-mode Profiling

תרגיל 4 — ה־TC מודד את עצמו

לוקחים את המתרגם של תרגיל 3, מוסיפים profiling stubs בתוך הקוד המתורגם, מתקנים את תשתית התרגום, ואז מקטינים overhead בעזרת liveness ו־dead-register elimination.

חזרה למסלולהבא: הפרויקט

1. הדרישות

  1. לרוץ בהצלחה על כל binaries של תרגיל 3.
  2. לא לשמור/לשחזר registers מתים שבהם משתמש instrumentation code.
  3. להפיק edge-profile.csv, hottest → coldest, עם taken/fall-through ועד 4 targets עקיפים.
  4. להסביר הבדלים גדולים לעומת profiler קודם.
  5. להציג שיפור של לפחות 5% במדד performance אחד לעומת הגרסה הלא־מותאמת.
האתגר הכפול: ה־Pintool גם מתרגם code נכון וגם מזריק code נוסף שרץ בקצב של היישום. כל bug ב־stub הוא bug בתוכנית; כל instruction מיותרת ב־stub חם היא overhead.

3. איך profiling stub עובד?

כל stub מתחיל ב־wide NOP של לפחות 5 bytes. בהתחלה הוא אינו עושה דבר, ולכן הביצוע ממשיך אל גוף ה־stub. לאחר -prof_time, ה־NOP נדרס ב־JMP rel32 שמדלג מעל כל entries מסוג ProfilingIns.

[wide NOP: reserved patch site]
[save live scratch state]
[optional: compute indirect target + update target table]
[increment BBL/fall-through counter]
[restore live scratch state]
[original instruction continues]

ספירת BBL

הגרסה השמרנית שומרת RAX, קוראת counter, מגדילה עם LEA שאינה משנה flags, כותבת ומחזירה RAX. אם ה־flags מתים, האופטימיזציה יכולה להשתמש ב־instruction יחידה:

ADD qword ptr [RIP + counter_disp], 1

ה־ADD משנה flags — ולכן היא חוקית רק כאשר liveness מוכיחה שהם מתים.

יעד indirect jump

ה־stub מחשב את target האמיתי אל RAX, שומר אותו, משתמש בשתי הסיביות הנמוכות כ־bucket index ‏0–3, שומר address ומגדיל count. המיסוך נעשה בגרסה המתוקנת עם SHLX/SHRX שאינן משנות RFLAGS.

המפה מקורבת: target & 3 גורם ל־targets שונים להתנגש. זה מספיק לדו״ח גס של תרגיל 4, אך לא בטוח לשריפת target בתוך de-virtualization בפרויקט.

4. האופטימיזציה — Liveness של scratch state

השאלה בכל נקודת stub היא: “אם אשמיד כרגע את RAX/RBX/RCX או flags, האם הקוד המקורי ישתמש בערך הישן לפני שייכתב ערך חדש?” אם לא — הערך מת, ואין צורך לשמור ולשחזר אותו.

איסוף read/kill

  • read של alias כמו AL/EAX נספר כ־read של RAX המלא לצורך שמרנות.
  • רק write של 64-bit או 32-bit zero-extending הורג register מלא.
  • write של 8/16-bit אינו הורג את החלק העליון.
  • predicated write כגון CMOV אינו kill ודאי.
  • flags נעקבים כיחידה של CF/PF/AF/ZF/SF/OF בעזרת metadata של XED.

משוואת dataflow

live_in[i] = reads[i] ∪ (live_out[i] − kills[i])

האלגוריתם רץ backwards עד fixpoint, משום ש־loops יוצרים תלות מעגלית. ב־branch תנאי, live_out הוא union של taken successor ו־fall-through successor.

Boundary conditions שמרניים

Control flowמה נחשב liveלמה
RETRAX ו־RBXreturn value ו־callee-saved state.
CALLמודל SysV: callee עשוי לקרוא RAX/RCX; RBX נשמרargument/caller/callee conventions.
Indirect JMPRAX/RBX/RCX ו־flagsה־target אינו ידוע ועשוי להשתמש בכולם.
Target מחוץ ל־routineהכולאין visibility על successor.

6. בניית edge-profile.csv

dump_profile עובר על bbl_map, מוצא את ה־instruction המקורית הראשונה שאינה stub, ומחשב:

  • conditional: taken = counter - fallthru_counter.
  • unconditional/ret: כל execution נחשב taken.
  • call או סוף סטטי אחר: כל execution נחשב fall-through.

target buckets לא ריקים ממוינים לפי count, וכל השורות ממוינות hottest → coldest.

7. תוצאות performance הקיימות

המדידה השוותה baseline עם כל תיקוני הנכונות אך ללא dead-register optimization מול הגרסה המותאמת. הריצות היו interleaved והושוו medians.

10.5%

8. התרומה לפרויקט הסופי

Profile in translated code

הפרויקט צריך לאסוף data ב־TC1 לפני בניית TC2.

Safe code emission

כל guard או reorder חייב לשמור registers/flags ולתקן displacement.

Runtime patching

wide NOP ו־patching מאפשרים מעבר ממצב מדידה למצב optimized.

תרגיל 4 הוא הבסיס הקרוב ביותר לפרויקט: הוא כבר משלב translator + profiler + timer + performance methodology. הפרויקט מוסיף “השתמש בפרופיל כדי לשנות את הקוד ב־TC2”, במקום רק להפסיק למדוד.

בדיקת הבנה

למה ADD [counter],1 אינה תמיד בטוחה?

היא משנה status flags. אם successor קורא flags שנוצרו לפני ה־stub, ה־ADD משנה semantics. משתמשים בה רק כש־flags provably dead.

למה wide NOP היא “load-bearing”?

היא שומרת מקום ידוע של לפחות 5 bytes שאפשר לדרוס ב־JMP rel32 מבלי להזיז את יתר הקוד. גם כיבוי profiling וגם gearing ל־TC2 תלויים במקום השמור.

למה profile של תרגיל 4 אינו זהה בהכרח לתרגיל 2?

JIT ו־Probe בונים גבולות BBL וכיסוי שונים; תרגיל 4 מתרגם בעיקר main image ומודד חלון זמן, בעוד תרגיל 2 מגלה code דינמית ומכסה libraries.

מתי liveness מאפשר למחוק save וגם restore של register?

כאשר ה־value הישן מת בנקודת ה־stub: אין שום path שבו הוא ייקרא לפני overwrite. אז ה־stub רשאי להשתמש ב־register כ־scratch בלי לשמר אותו.

למה patch של JMP בן חמישה bytes מתוך timer thread עלול לקרוס?

Thread היישום יכול fetch את ה־opcode החדש יחד עם displacement שנכתב רק חלקית. המימוש מכין את ה־bytes מראש ומבצע את ה־patch ב־signal handler על application thread.

למה indirect jump מחייב הנחת liveness שמרנית במיוחד?

ה־target אינו ידוע סטטית ועלול לקרוא registers ו־flags שהיו חיים לפני הקפיצה. תרגיל 4 אף מצא מקרה אמיתי שבו sgcc_peak נשא flags דרך indirect jump.

איך מוכיחים שהאופטימיזציה של stubs לא רק מהירה אלא גם נכונה?

משאירים profiling פעיל לאורך כל הריצה, משווים את profile הכלי המותאם ל־baseline על workload דטרמיניסטי, ובמקביל דורשים פלט תוכנית byte-identical ו־TC verifier נקי.
